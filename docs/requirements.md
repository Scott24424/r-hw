## 6. UR-16이 바꾼 데이터 모델 (AP-03 거절의 결과)

**시간표는 더 이상 "날짜 없이 매일 반복되는" 것이 아니다.** 변경 범위를 한곳에 모은다.

| 대상 | 변경 전 | 변경 후 |
|---|---|---|
| `ScheduleBlock` 컬럼 | `id, startMinute, endMinute, label, kind, matchType, createdAt, updatedAt` (8개) | **`date`가 추가되어 9개.** `id` 다음, `startMinute` 앞 |
| `ScheduleBlock` 인덱스 | `@@index([startMinute])` | **`@@index([date, startMinute])`** — "이 날짜의 시간표를 시간 순서로"가 주 질의다 (UR-16.2, UR-08) |
| 겹침 불변식 I9 | 모든 범위 블록끼리 | **같은 `date` 안의 범위 블록끼리.** 다른 날짜의 블록은 겹침 판정 대상이 아니다 |
| D11 매칭 규칙 | 블록(날짜 없음) × 날짜 D | **날짜 D의 블록** × 같은 날짜 D의 과제. 규칙이 단순해진다 |
| 시간표 API | `GET /api/schedule/blocks` (전체) | **`GET /api/schedule/blocks?date=`** (필수 필터) |
| 시간표 화면 | 매일 같은 시간표 | **날짜별 시간표.** 블록이 없는 날은 "이 날짜의 시간표가 없음" |
| 시드 블록 10건 | 날짜 없음 | **한 날짜(`2026-07-29`)에 10건** (UR-26). 다른 19일은 비어 있으며 이는 의도된 동작이다 (UR-26.2, UR-26.4) |
| D1의 분리 근거 | "시간표엔 날짜가 없다" | **"시간표엔 상태가 없다".** 날짜는 이제 양쪽에 있으므로 분리 근거에서 뺀다 |

**엔티티 분리 자체는 유지된다.** 근거가 "날짜 유무"에서 "상태 유무 + 생명주기"로 좁아질 뿐이다. `Assignment`에는 상태 전이(UR-17)가 있고 `ScheduleBlock`에는 없다.

### 7.1 OPEN-02 — 결정된 `bulk-status` 일부 실패 정책

**요구는 `UR-25.3`이, 값은 `UR-25.4`·`UR-25.5`가 담는다.** `UR-25.3`은 "일부 항목 실패 시 처리 방식을 **명세와 테스트에서 결정적으로 정의**하라"고 요구할 뿐 무엇으로 정의할지는 지정하지 않았다 — 그 값이 `OPEN-02`였고, **2026-08-01 사용자 승인으로 아래와 같이 확정**되었다.

| 결정 항목 | 후보 | **승인된 값** |
|---|---|---|
| **OPEN-02.1** 실패 원자성 | A. 전부 성공하거나 전부 롤백 / B. 성공분만 반영하고 실패 목록 반환 | **A — 전부 성공하거나 전부 롤백** (`UR-25.4`) |
| **OPEN-02.2** 동일 상태 재적용 | A. 멱등 no-op으로 성공 집계 / B. 전이 규칙 위반으로 실패 | **A — 성공하는 멱등 no-op** (`UR-25.5`) |

**두 값이 함께 성립해야 하는 이유.** 부록 C.3의 주 사용 시나리오는 "지난 날짜를 한 번에 정리"인데, 그 날짜에 이미 완료된 과제가 섞여 있는 것이 정상이다. `UR-25.5`(동일 상태 = 성공)가 없으면 `UR-25.4`(전부 롤백)와 만나 **주 시나리오가 거의 항상 실패**한다. 두 조건은 분리해서 반영할 수 없다.

**`UR-25.2`와 충돌하지 않는다.** 동일 상태 재적용은 §3.2 전이 행렬의 대각선(`–`)에 해당하지만, `UR-25.5`는 그것을 **"전이를 수행하지 않는다"** 로 해석할 뿐 단일 전이 규칙 자체를 바꾸지 않는다. 실제 상태를 바꾸는 항목은 전부 단일 전이 검증을 그대로 통과해야 한다.

**적용 경계.** MVP에는 계정 인증·권한 분리가 없으므로(`UR-19.1`, `NR-04`) 이 정책은 **권한 판정이 아니라 요청 단위 실패 처리**에 대한 것이다. `UR-25.4`가 "권한 오류"를 실제 실패로 열거한 것은 **후속에 인증이 도입될 때의 분류**를 미리 고정한 것이며, MVP에서 인증을 요구한다는 뜻이 아니다. 화면상의 접근 제한은 `UR-25.1`(부모용 화면에만 배치)이 담당한다.

**정책 값과 API 실패 분류는 다른 층이다 (R3-01).** `UR-25.4`·`UR-25.5`는 **정책 값**이며 이번 라운드에서 바뀌지 않았다. 그 값을 현재 `{ date, to }` 요청 모델로 옮길 때 네 실패 유형이 어디로 가는지(검증 오류 → 요청 수준 400, 허용되지 않는 전이 → 항목 수준 409, 존재하지 않는 과제·권한 오류 → 현재 계약에서 발생 불가, 빈 날짜 → 성공하는 빈 batch 200)는 **설계 층의 사상**이며 `architecture.md` §5.2와 `decisions.md` D22에 있다. 이 문서가 그 HTTP 코드를 정의하지 않는다.

**반영 위치와 담당.** 설계 결정은 [`decisions.md` D22](./decisions.md#d22), API 계약은 `architecture.md` §5.2, 사용 맥락과 최소 테스트 조건은 `architecture.md` 부록 C.3와 §7.2다. 구현 담당은 **엔드포인트가 T09**(예약 번호), **진입 화면이 T17**(예약 번호)이며 **둘 다 배치 1(T01~T04)의 범위 밖**이다 — 이 결정으로 T01~T04의 범위는 바뀌지 않는다.

### 7.2 OPEN-01의 경과 (닫힘)

`daily-schedule.jpg`에는 날짜가 없고(MR-20), `UR-24.5`가 블록 수를 10건으로 고정하므로 시드는 **한 날짜분**이어야 했다 — 20일 전체에 넣으면 200건이 되어 충돌한다. 남은 것은 날짜 값 하나였고, 사용자가 **파일럿 기간 첫날을 대표 일일 시간표 날짜로 명시적으로 지정**해 확정했다.

**`2026-07-29`는 이미지에서 판독한 값이 아니다** (UR-26). 설계·시드·문서 어디에서도 "사진에서 이 날짜를 읽었다"고 쓰지 않는다. `2026`이라는 연도에 대한 `UR-15.3`과 같은 성질이다.

**다른 19일이 비어 있는 것은 의도된 동작이다** (UR-26.2, UR-26.4). 결함이 아니며 완료 보고에서 실패로 보고하지 않는다. 시간표 템플릿·반복이 MVP 밖이므로(UR-26.3, NR-03) 사용자가 날짜별로 입력한다 (UR-26.5).

## 9. 이 문서를 고치는 규칙

1. `UR`·`OR`·`NR`은 **사용자만** 추가·수정·삭제할 수 있다.
2. `MR`은 이미지를 다시 관찰해 정정할 수 있으나, **추측으로 채우지 않는다.**
3. `OPEN`은 사용자 확인 시 해당 `UR`로 흡수한다.
4. 설계 문서에서 이 문서로의 **역방향 승격을 금지**한다.
5. 결정을 뒤집을 때는 `decisions.md` 상단 규칙대로 **항목을 지우지 말고 뒤집은 이유와 함께 갱신**한다.
